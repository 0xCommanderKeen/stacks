# Recoverable Trash

Move a book to Trash from its detail page after opening “Remove from your catalog.” Its notes, ratings, tags, collections, series memberships, reading records, representation IDs, asset IDs and saved listening position remain. Library/Archive search, run browsing, collection browsing and Home omit trashed works. Direct work pages explain the state and offer recovery. Restore makes the original identities visible again.

Managed originals move into the owned `.trash/<operation-id>/` directory. Read-only registrations are only hidden; Stacks never changes their source files and does not need a working source mount to hide or restore them. Mixed works move only their managed originals. Derived covers remain in owned storage with their existing references. Reimporting identical bytes resolves the existing trashed owner and does not silently create or restore a work.

Schema0011/export11 adds `Work.trashed_at`, `TrashOperation`, and a `TrashFile` checkpoint per managed asset. A request snapshots original locations and hashes with SQL insert/select and hides the work in one transaction. Restore reverses the last completed trash manifest. Per-file paths and completion markers commit together. The work becomes visible only after all restored originals have been verified.

The existing single intake worker prioritizes one relocation file between other jobs. It shares the ingestion mutex for file ownership changes, while hashing stays outside the catalog mutex. A verified same-filesystem hard link publishes each destination exclusively, then directory fsync and source unlink finish the move. It never overwrites an unexpected destination, even when its bytes happen to match. Recovery handles source-only, both names referring to the same inode, and destination-only states. Changed bytes, symlinks, collisions, permissions and storage failures leave an actionable interrupted operation with retry. Shutdown checks during hashing preserve the durable checkpoint; restart resumes queued/running operations. There is no permanent-delete action.

Catalog editing/grouping refuses trashed works. Catalog-operation snapshots include trash history so an old undo cannot erase newer storage receipts, including after restore. In-flight progress saves can retain the last heard position; new downloads/playback/stream requests require restoration. The web action releases the currently selected audiobook after saving its position.

Full backups refuse unfinished relocations and verify completed trash originals along with other owned files. Backups and portable export retain trash history and file locations; a fresh restored library can restore a trashed book normally. External originals still require independent source protection.

Trash is server-paginated with search, persistent URLs and recovery progress/errors. Completing a restore on the final page moves to the last remaining populated page. Tests cover exact identity and curation preservation, missing mounts, mixed storage, disk/permission/collision failures, interruption before catalog acknowledgement, actual restart, concurrent catalog access, audio progress, guarded grouping undo, authenticated APIs, fresh backup restoration, and desktop/phone removal/restore journeys.
